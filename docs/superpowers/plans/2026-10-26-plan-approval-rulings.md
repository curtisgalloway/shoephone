# Plan approval: rulings made during the build

Decisions the build controller took on the operator's behalf while executing
`2026-10-26-plan-approval.md`, each with its reason and what it costs if wrong.
The spec's "Changes during the build" section records the ones that changed
behavior; this is the full list.

- Ruling 1: Every transition out of Queued, Working or Waiting (to Waiting excluded only when staying pending) releases the gate slot except Queued→Working→Waiting, which keep it until a verdict, a refusal, a plan failure, a timeout or a kill — the slot means "a request is awaiting a verdict or its plan", and leaving it held would block all SSH requests — if wrong: an SSH request is refused Busy, or admitted early, during a job.
- Ruling 2: Add Push::JobRequested (record, kind `job_requested`, body "A deploy request was filed.") for JobEvent::Requested; JobEvent::Started maps to PlanStarted. Every ledger event pushes (AGENTS.md invariant) and Started is the plan-start moment the spec names — if wrong: one extra passive push kind on the phone.
- Ruling 3: Task 16's dispatch carries the requirement to call context_digest at plan time and compare it at claim, failing with context_changed — the plan put the function in Task 15 and the loop that claims is Task 16 — if wrong: none; it is the spec's pinned-context rule.
- Ruling 4: Apply scope counts/destructive must agree with the address text: Task 7 daemon refuses a submit whose counts or destructive flag differ from what display.address_text implies (and refuses if any scope fails is_well_formed); Task 9 page derives counts/destructive from the address text it hashes and refuses to sign on mismatch; Task 14/16 build all three from one change list — from the automated security review of src/scope.rs (signed fields could drift from the list shown) — if wrong: one redundant check per apply.
- Ruling 5: Fix task 2b runs right after Task 3 (not in parallel, same worktree): bytes_to_sign on TrustScope/ApplyScope returns Option<Vec<u8>> (None unless is_well_formed); project names must match [A-Za-z0-9._-]{1,64}; other free-text fields (addresses) reject control chars plus U+0085, U+2028, U+2029, U+200E, U+200F, U+202A-U+202E, U+2066-U+2069; tests for each — from the automated security review (debug_assert compiled out of release; Unicode line/bidi separators pass clean()) — if wrong: callers in Tasks 7-9 handle an Option they could have skipped.
- Ruling 6: Task 2b fixture conflict (all vectors use project "infra/web", brief forbids "/") — rename to "infra-web" and regenerate vectors independently — project names are runner config keys and need no "/"; the app has not vendored the file yet — if wrong: a project name with "/" is refused, rename it.
- Ruling 7: JobEvent::Started and ::Waiting gain kind: &'static str so the ledger can write trust_/apply_ kinds; trust Started is ledgered review_started, apply Started plan_started — the plan listed kinds the events could not produce — if wrong: two ledger kind names to rename.
- Ruling 8: Task 4 untrust refuses while the daemon listens, which contradicts Task 7 live untrust — carried into Task 7: remove the guard and its messages; serialize trusted.json read-modify-write between daemon and untrust with an advisory flock on state_dir/trusted.lock; write_atomic_private removes any stale temp and opens with create_new — Task 4 alone is consistent; the fix belongs where the live re-read lands — if wrong: an untrust racing a trust approve is lost, or a stale temp keeps a wider mode.
- Ruling 9: Task 5 adds Refusal::StaleSignature (401) for bad timestamp or replayed nonce, distinct from Refusal::Stale (context changed); nonce cache bounded (120 s, 10,000 entries, refuse past cap); nonce recorded only after signature verifies — the plan named Stale for both meanings, and an unbounded or pre-auth cache is a memory-exhaustion path — if wrong: one extra refusal variant.
- Ruling 10: Carried into Task 7: (1) Jobs drops an Apply job's manifest text when it reaches Done and prunes Done entries older than 1 hour (CLI polls finish well inside that) with a test; (2) /api/trust and /api/apply run a read-only Jobs pre-check (known project, no active job, not cooling down) before decoding or hashing the archive; (3) the manifest-value test also covers a trust reply — Task 6 review Important was Task 3 state retaining Done jobs and manifests (reachable from the unauthenticated endpoint) — if wrong: up to ~9 MiB/day resident, and manifest text kept in memory.
- Ruling 11: Task 7 split into 7a (brief + Ruling 4 consistency checks + is_well_formed + set_trusted on Trusted finish) and 7b (Rulings 8 and 10 hardening), run sequentially — one dispatch carrying all of it is too broad to review well — if wrong: one extra review cycle.
- Ruling 12: In-handler WrongRunner from Jobs (authenticated runner, another runner's job) stays 403; only authentication failures on runner routes are 401 — 403 is the accurate status and Ruling 9 concerned authentication — if wrong: a status code to change.
- Ruling 13: Carried into 7b from the 7a re-review: (1) finish(trusted) restores the previous trusted.json and in-memory trust when the ledger append fails, so a 503 means the trust did not take effect; (2) a non-external trust display may not carry verify_command; (3) the finish pre-check uses Jobs' own runner_of mapping — closes the remaining audit gap and an unbound display string — if wrong: one more rollback path to maintain.
- Ruling 14: A trust record with no `trusted` ledger entry for its job is dropped at daemon startup (reconcile), and a failed runtime restore sets that project's in-memory trust to None — closes the disk-full case where the rollback cannot write; the audit trail is authoritative — if wrong: a legitimately trusted revision is dropped after a ledger loss and must be re-trusted.
- Ruling 15: Task 8 push mapping for job events: Requested → JobRequested (new, record), Started → PlanStarted, Waiting{trust|apply} → TrustWaiting|ApplyWaiting (only interrupting ones), Approved → JobApproved (new, record), Killed → JobKilled (new, record), others as the plan names; untrust writes an `untrusted` ledger line from the console with one O_APPEND write — every ledger event pushes (AGENTS.md) and the plan left Approved/Killed unmapped for jobs; the console cannot push, so the phone sees untrust in its ledger view — if wrong: three push kind names to rename, and untrust is visible only on the next ledger fetch.
- Ruling 16: The page refuses manifest numbers outside the IEEE-double safe range (integers beyond 2^53, decimals over 15 significant digits); Task 12 schema validation applies the same limits to number variables so a valid manifest is always displayable — the page cannot show a precision-only change honestly — if wrong: a schema with high-precision numbers must use strings.
- Ruling 17: In the trust diff block, a literal backslash is escaped only before u or U (the only spoofable sequence); elsewhere it shows as written so reviewed source keeps its fidelity — doubling every backslash misrepresents the code under review — if wrong: one more character class to escape.
- Ruling 18 (supersedes Ruling 16 and amends 17): the variable diff compares the raw canonical value text of each key (no reparse), so no precision collapse is possible; the page refuses only non-finite numbers; the 15-significant-digit and subnormal refusals are removed; the diff block doubles a backslash before u, U, or any character the page escapes; the hold timer is keyed to a render generation — exact text comparison removes the class of number bugs instead of patching cases, and my Ruling 17 opened the backslash hole — if wrong: two values with equal numbers but different spellings show as a change.
- Ruling 19: The upload is a gzip tar from `git archive` (tracked files of HEAD, no history), not a git bundle as the spec's Terms say; the spec text is corrected in Task 18 — a tar has no object graph to bound and carries no history, and the plan and CLI already use it — if wrong: the CLI and unpack switch formats.
- Ruling 20: The trusted tree and every Terraform run use ONLY the execution-input files (project dir plus local module dirs), copied out of the checkout by a new `copy_execution_input`; files outside them are absent at plan time, so a read outside fails the plan instead of running unreviewed content — the spec says execution input includes "any file the configuration reads", and materializing only the digested set makes that true by construction without bloating trust diffs — if wrong: a configuration that reads a shared file outside its directory must move it into a module directory.
- Ruling 21: Manifest canonical form for Task 12 — JSON object, keys sorted by code point, no whitespace, all schema keys present, integers emitted exactly (never via f64), integers beyond 2^53-1 and non-finite numbers refused, schema variable names ^[a-z_][a-z0-9_]{0,63}$, strings refuse control and bidi/invisible characters — the approve page compares raw per-key text and must render every accepted value exactly — if wrong: a schema needing large integers or exotic names must use strings.
- Ruling 22: canonical numbers normalize — an integral finite float within the safe range renders as an integer, -0.0 as 0 — so equal values render the same bytes and the approve page never shows an unchanged value as changed — if wrong: a variable that must distinguish 1 from 1.0 needs to be a string.
- Ruling 23: the operator verification verb is `shoephone-runner diff-digest <baseline-digest|none> <baseline-checkout|-> <candidate-checkout> <project-path>`: it recomputes each checkout's execution input, refuses unless the baseline checkout's digest equals the given digest, and prints the candidate digest and the diff digest for the operator to compare with the page; Task 13 also updates the approve page's command text to this form with placeholders for the two checkouts — a digest alone cannot reconstruct the baseline tree — if wrong: the page shows a command the operator cannot run.
- Ruling 24: diff header paths containing a space, double quote or backslash are written in git C-style quoted form on every header line, so a header line reads one way — paths may legally contain spaces — if wrong: header format changes again while still unbound by any deployment.
- Ruling 25: an archive entry under a root .git is refused at unpack (archive_entry_refused) — git archive never emits one, so its presence means a hand-built archive, and both sides now ignore a root .git consistently — if wrong: none for real git exports.
- Ruling 26: plan summary fails closed on any action list it does not recognize (plan_unknown_action), includes non-no-op output_changes as output.<name> changes, refuses addresses over 512 chars or with forbidden characters (plan_address_refused), and is the only source of counts, destructive flag and address text — an unrecognized action or a hidden output change must never pass unseen by the approver — if wrong: a newer Terraform action needs an explicit mapping before it can be applied.
- Ruling 27: output.<name> changes count in Counts and the destructive flag like resources, so the signed address text, the daemon's consistency check and the page's derivation stay one rule; removing an output therefore needs --allow-destroy — one counting rule across three components beats a special case — if wrong: an extra flag on applies that only drop an output.
- Ruling 28: Task 15 Step 5 (manual check that the real bwrap sandbox hides the runner key and config from Terraform) cannot run on this macOS controller host (no bubblewrap); the code and its pass-through-stub tests proceed, and the real-sandbox check is recorded UNVERIFIED and must run on a Linux host before deployment — reaching another Linux machine from here is an outward action outside this task — if wrong: the sandbox may expose the token until that check runs.
- Ruling 29: the executor sandbox bypass compiles only under cfg(any(test, feature = "test-hooks")) so Task 16's integration tests can drive it, mirroring the daemon's test-hooks route; a deployed build never enables test-hooks (AGENTS.md) — integration tests are a separate crate and cannot see cfg(test) — if wrong: a release built with --features test-hooks could skip the sandbox, which AGENTS.md already forbids.
- Ruling 28 (widened): besides the real-bwrap test, the Linux-only code paths (siginfo si_pid, bwrap fd binding) have not been type-checked: this macOS host has no container runtime and cross-checking fails in ring's build script. Before deployment, on a Linux host: `cargo test` (full) and `cargo test bwrap_hides_runner_secrets -- --ignored` — if wrong: a Linux-only compile error or sandbox gap ships undetected.
- Ruling 30: the runner refuses a daemon URL that is not https:// unless its host is loopback — the runner acts on daemon replies, so the channel must be authenticated — if wrong: a test or lab setup must use loopback or TLS.
- Ruling 31: root recomputes the trust review itself (diff digest and summary counts, from its own unpack of the fetched archive against trusted/) before submit and again at install, refusing review_inconsistent on any mismatch with the worker; the worker's remaining role is the warnings and display text. Root therefore parses archive content (tar, HCL module scan, text diff) — an accepted, documented deviation from the spec's "resolver never parses repository content", because a lying worker otherwise defeats the operator's review; the parsers are memory-safe Rust bounded by Limits — if wrong: a parser bug runs in root rather than in review_user.
- Ruling 32: a Claimed job the daemon never hears from lapses after claim_ttl (default 3 h, above three 60-minute Terraform timeouts) to OutcomeUnknown, with ledger event and push, releasing the one-job slot; and the runner journals every claim (trust and apply) and every unreported result, retrying finish with backoff before polling new work, and re-sending at startup — a lost finish otherwise blocks all work and drops the audit record — if wrong: a genuinely running apply past 3 h is reported unknown while still running.
- Ruling 33: Task 16b — reviewer warnings reach the approver: root's own review (Ruling 31) supplies them, DisplayWire gains structured warnings, the daemon validates their shape, and the trust screen shows them labeled as unsigned runner findings — the spec puts the warnings in the trust review; they are advisory, so they are displayed but not signed — if wrong: warnings would need to enter the signed trust scope.
- Ruling 34: `shoephone trust` refuses only tracked changes (`git status --porcelain --untracked-files=no` non-empty), since `git archive HEAD` never includes untracked files; it archives the whole repository at HEAD and refuses before upload if the gzip exceeds 16 MiB (exit 30, archive_too_large) — untracked scratch files are common and cannot reach the runner anyway — if wrong: an operator expecting untracked files to block is surprised.
- Ruling 35: imports and moved renames in a plan (change.importing, previous_address) are refused with plan_import_refused / plan_move_refused rather than shown, because the signed apply format has no action word for them and adding one changes the scope format the app vendors — if wrong: an apply that imports or moves must be split into a trust-reviewed change with the import or move removed.
- Parked: CLI exit 22 message says "nothing ran" when it cannot know (approval+claim+daemon restart inside one poll gap) — Ruling 36: left as is for this branch; listed for the operator — fails toward a retry the daemon would refuse as busy/no trust — if wrong: an agent retries a job that may have applied.
- Parked: ledger can hold applied and outcome_unknown for one id after a lost reply — Ruling 37: accepted; both are in the safe direction and the phone shows both — if wrong: the operator sees a contradictory pair and must check state.
- Parked: one jobs.rs assertion on "untrusted" is vacuous; status assertions and the unit test cover the refusal — Ruling 38: accepted for this branch — if wrong: a regression in that refusal event is caught only by the other assertions.
